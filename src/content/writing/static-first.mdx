过去几年我默认的起手式是「Next.js + TypeScript + Tailwind」。这个选择不算错，但它把很多**本来不需要运行时**的问题，提前变成了运行时问题。

现在我的默认顺序反过来了：先假设它是静态的，只有当交互真的需要服务端状态时，才引入框架。

## 三个数据点

数字来自同内容移植的实测，不是理论推算：

| 场景 | 静态生成 | 全栈框架 |
| --- | --- | --- |
| 同一篇博客的 JS 体积 | 11 KB | 92 KB |
| 同一篇博客 Lighthouse（移动端） | 99 | 84 |
| 同一张落地页 | 6 KB | 214 KB |

差距不在「框架不好」，而在于框架默认要为**将来可能存在的交互**付费：客户端运行时、路由、水合、边界协议。而一个内容页面 90% 的交互，其实只有「点击跳转」。

## 静态优先不等于没有交互

静态站点仍然可以有多数人以为必须上框架的能力：

- **搜索**：构建期生成倒排索引，运行时只加载一个几十 KB 的 WASM 检索器（Pagefind 就是这么做的）。
- **评论**：第三方脚本（Giscus）挂在文章底部，和页面本身的构建无关。
- **表单**：提交到边缘函数或第三方表单服务，返回值用原生 `fetch` 处理。
- **主题**：一个几十行的运行时加首帧内联脚本，不需要 React。
- **页面转场**：跨文档 View Transitions 已经是 CSS 标准，`@view-transition { navigation: auto; }` 一行就够。

这些能力加起来的总量，通常仍小于一个框架的客户端运行时基线。

## 什么时候该上框架

反过来，这几种情况我会直接用服务端渲染：

1. **页面内容依赖登录态**，而且每个用户不同。静态生成会把别人的数据发给你。
2. **需要实时或高频变化的服务端状态**：购物车、协作编辑、行情。
3. **强交互的单页应用**，客户端状态机本身就是产品主体。
4. **团队已经在框架上**。迁移成本大于收益时，不要为了「更先进」重写。

判断方法很简单：把页面上的交互一条条写下来，标出哪些需要服务端读数据。如果一条都没有，或者只有「提交后跳转」，那它就是静态页面。

## Astro 的取舍

Astro 的模型是「默认零 JS，按需加岛屿」。这个模型的价值不在语法，在于它让「加 JavaScript」变成一个需要解释的动作：

```astro
---
// 构建期执行，不进浏览器
const posts = await getCollection('writing')
---

<ul>
  {posts.map((post) => <li>{post.data.title}</li>)}
</ul>
```

上面的组件在构建后是一段纯 HTML。要加交互，必须显式写 `client:load` 之类的指令——这个显式性本身就是文档，审阅代码的人一眼能看出「这一块会进浏览器」。

代价也要说清楚：Astro 不适合做重客户端应用。状态会在页面之间丢失，跨页面的局部刷新需要自己设计，成熟组件生态比 React 小一个数量级。**它是内容站的工具，不是应用的工具。**

## 我的默认清单

新项目开始时按顺序问：

1. 内容在构建时就能确定吗？能 → 静态生成。
2. 需要客户端交互吗？需要 → 岛屿，按块加。
3. 有登录态或实时数据吗？有 → 边缘函数或 SSR，但仍然只给需要的路由。
4. 上面三步之后，还剩下复杂到必须用框架的东西吗？通常没有了。

框架不是错的，它只是贵。贵的部分应该在需要的时候再付。
